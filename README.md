# 핀프렌즈 SRS 저장소

**핀프렌즈(FinFriends) PRD v1.0** 을 **SRS 문서로 변환하고, 실행 가능한 태스크까지 분해**하는 작업 저장소입니다.

---

## 1. 작업 목표

### 1.1 하는 일

> **기준 템플릿은 `[SRS 문서] AD-Core-Platform (한글).md` 하나입니다.**

`finfriends-prd-v1_0.md` 에 담긴 내용을, 예시 SRS 문서가 이미 쓰고 있는 **섹션 구성 · 표 스키마 · ID 체계 · 서술 톤**으로 옮겨 적습니다. 도메인만 다를 뿐(광고 플랫폼 → 아동 금융교육), 문서의 **뼈대는 예시 문서를 그대로 따릅니다.**

### 1.2 하지 않는 일

**ISO/IEC/IEEE 29148:2018 표준을 전부 만족하는 풀 스펙 SRS를 쓰는 것이 목표가 아닙니다.**

표준이 요구하는 전체 섹션을 빠짐없이 채우는 방향으로 문서를 부풀리지 않습니다. 예시 SRS가 다루지 않은 영역은 아래 1.3의 확장 규칙에 해당하지 않는 한 **쓰지 않습니다.**

### 1.3 확장 규칙

PRD에는 예시 SRS의 7개 섹션 어디에도 자연스럽게 들어가지 않는 내용이 있습니다. 버리지 않되, 임의의 형식으로 덧붙이지도 않습니다.

| 상황 | 처리 |
| --- | --- |
| 예시 SRS에 대응 섹션이 있음 | 예시 포맷 그대로 채움 |
| 예시 SRS에 대응 섹션이 없음 | **그 부분만** 29148 표준 구성에 따라 섹션 신설 |
| PRD에 없는데 예시 SRS에는 있는 항목 | 억지로 만들지 않고 미정으로 표기 |

확장으로 신설한 섹션은 **어느 표준 조항을 근거로 추가했는지 문서 안에 밝힙니다.**

### 1.4 승계한 제약 5항

입력 PRD가 명시한 제약을 SRS로 옮길 때에도 유지합니다.

1. **결정과 수치를 구분한다** — §4 기능 우선순위 · 규제 상수 · 범위 · ADR 8건은 **확정된 결정**이므로 확정 사양으로 옮기고, **기준선은 실측 전**이므로 목표값을 달성한 성과처럼 적지 않습니다.
2. **성능 · 가용성은 AC 역산 상한** — 확정 SLO가 아니라 *"이 값을 넘으면 해당 AC가 성립하지 않는다"* 는 상한입니다(ADR-007). 그 지위를 함께 적습니다.
3. **인용 금지 10항목** — PRD §9-2의 금지선을 그대로 승계했습니다(중립판 §1.4 ③). 특히 **「소비 순간 자동 개입」은 폐기된 기능**이며 로드맵에도 없습니다(ADR-002).
4. **미대응 상태 노출** — 사전 개입 사각지대는 계획 카드로 **부분 대응**이며 **자동 발동은 0개**입니다. 해소된 것처럼 기술하지 않습니다.
5. **등급 표기 승계** — `[A]` `[관측]` `[추론]` `[검증 대기]` `[설계 확정]` ✍️`[합성 가설]` 🧪`[모의]`

## 4. 입력 PRD 개요

- **제품:** 핀프렌즈 — *"배운 것을 실천할 자리를 만든다"*
- **두 가치 선언:** ① 아이에게 **성장이 일어난다** ② 그 성장이 보호자에게 **보인다**
- **북극성 KPI:** WPA(주간 실천 인정 아동 비율) — β 기준 ≥ 5/8 · 일반 공개 ≥ 55%
- **기능 범위:** F1–F18 · Must 8 / Should 5 / Could 3 / Won't 1 = **17건**
- **유저 스토리:** US-1 ~ US-8 · AC 26건 + 예외 AC 17건 = 43건
- **ADR:** 8건 (각 결정에 서 있는 가설 · 판정 실험 · 뒤집히는 조건 · 대가)

### 변환 시 유의점

PRD의 **결정은 확정**이지만 **기준선은 실측 전**입니다. SRS의 인수 기준에 수치를 옮길 때 확정 사양이 아니라 **실측 후 확정 대상**임이 드러나게 표기했습니다(중립판 §1.4 ①).

중립판이 **무엇을 만들 것인가**를 정의한다면, 이 문서는 **주어진 스택으로 어떻게 성립시킬 것인가**를 정의합니다. 원본을 대체하지 않는 **병렬 문서**입니다.

제약을 정확히 적용하면 중립판 요구사항 일부가 **그대로는 성립하지 않습니다.** 숨기지 않고 §8 대장에 전량 기록했습니다.

### 신설 요소

- **REQ-TEC-001 ~ 015** — 제약을 검증 가능한 요구사항으로 전환. 이 중 **5건은 위반 시 빌드 실패**
- **ADR-T01 ~ T10** — 제약을 만족시키기 위한 기술 결정 기록
- **§8 제약 충돌 해소 대장** — 스택 밖 6건(X1~X6) · 스택 내 7건(Y1~Y7) · **미해소 3건**(D-01 문자 채널 · D-02 온콜 Webhook · D-03 본인인증 위임)

**Next.js에 스케줄러가 없고** Vercel Cron 무료 요금제는 일 1회라 발송 지연 요건(p95 ≤ 6시간)을 못 맞춥니다. **Supabase `pg_cron` + `pg_net`** 으로 `/api/cron/*` 를 깨우는 방식을 채택해 **스택을 넓히지 않고** 4시간 주기를 만들었습니다(ADR-T02).

## 8. 설계 문서 (SDD)

`docs/[설계 문서] 핀프렌즈 (한글).md` — **1,461줄 · 다이어그램 32개**

SRS의 요구사항을 **어떻게 구현할지**를 그림으로 정리했고, **새 요구사항은 만들지 않았습니다.**

### 추적성 규율

클래스명을 **SRS §5 추적성 매트릭스와 일치**시켰습니다. 검사 결과 SRS가 지목한 **구현 단위 47종이 전부 SDD 클래스로 존재**합니다. SDD가 새로 도입한 2종(`EventCollector` · `ConsentState`)은 요구사항을 늘린 것이 아니라 구현을 나눈 결과이므로 §9에 각주로 남겼습니다.

> **검사가 실제로 잡아낸 것** — 초안에서 `AttendanceTracker` · `CycleResetScheduler` · `CopyReviewChecklist` 3종이 빠져 있었습니다. SRS는 지목하는데 설계에는 없는 상태였고, 검사가 이를 지목해 채웠습니다.

## 10. 개발 실행 계획

`docs/[총괄] 개발 실행 계획.md` — 태스크 67건을 **누가 · 어떤 순서로 · 언제** 만드는지 정의합니다.

| 항목 | 값 |
| --- | :-: |
| 총 공수 | **241 person-day** |
| DAG 레벨 | **12단계** |
| **임계 경로** | **46영업일** |
| 자원 제약 완료 | **91영업일** |
| 트랙 구성 | **6레인** — 플랫폼1 · 백엔드2 · 프론트1 · 디자인1 · QA1 |

### 이 계산이 드러낸 것

**임계 경로 46일과 자원 제약 완료 91일의 차이가 곧 인력 병목입니다.** 의존성만 보면 46일이면 끝나는 일을, 백엔드 2명 구성에서는 91일이 걸립니다. 백엔드 계열(Contract · Data · Write · Read) 태스크가 35건으로 몰려 있기 때문입니다.

즉 **일정을 당기려면 백엔드 레인을 늘려야 하고, 다른 레인 증원은 완료일을 앞당기지 못합니다.**

### 실행 4원칙

1. **게이트 우선** — `TEC-001` 제약 게이트를 가장 먼저. 나중에 세우면 그때까지의 위반이 한꺼번에 드러납니다
2. **계약 우선** — `CTR-001` · `CTR-002` 가 없으면 두 태스크가 같은 계약을 다르게 구현해도 탐지되지 않습니다
3. **디자인 선행** — `UX-001` 은 선행이 없습니다. 프론트가 대기하지 않도록 첫날 착수합니다
4. **규제 먼저** — `CON-002` 동의 게이트는 아동 화면 전부의 선행 조건입니다

### 검증

선행-후행 시간 역전 **0건** · 레인 내 시간 중복 **0건** · Gantt 배치 **67/67** · DAG 노드 **67/67**.
